## Project Overview

**Outdoor Team - Academia de Hábitos Saludables** is a full-stack health and wellness tracking application built as both a web app (PWA) and Android app (APK via Capacitor). The V2.0 system uses a **Vitality Points (PV)** gamification system based on METs (Metabolic Equivalent of Task) for physical activities and mindfulness practices.

**Stack:**
- Frontend: React 18 + TypeScript + Vite + TailwindCSS + Radix UI
- Backend: Node.js + Express + TypeScript
- Database: PostgreSQL via Supabase
- Mobile: Capacitor 7 for Android builds
- State Management: TanStack Query (React Query)
- Database ORM: Kysely

## Architecture

### Dual Configuration System (Web vs Mobile)

The project uses **two separate Capacitor configurations**:

1. **`capacitor.config.ts`** (Production/Build): No `server.url`, uses local bundled assets
2. **`capacitor.config.dev.ts`** (Development): Has `server.url: http://10.0.2.2:3000` for live reload

**Key Script**: `scripts/run-capacitor.js` automatically swaps configs based on environment (`prod` or `dev`), runs Capacitor commands, then reverts the config file.

### Backend API Organization

APIs are organized by feature domain in `server/routes/`:

**V2.0 Core APIs** (Vitality Points System):
- `activities-routes.ts`: 65+ METs-based activities catalog, registration, history
- `training-blocks-routes.ts`: 36 pre-defined 10-minute training blocks (HIIT, Strength, Aerobic, Seniors, Stretching, Relaxation)
- `vitality-routes.ts`: Weekly/daily PV tracking, calendar views
- `evaluations-routes.ts`: Health evaluations (IMC, PARQ+, IPAQ, PSS-10, WHOQOL-BREF)

**Legacy APIs** (to be phased out):
- `daily-habits-routes.ts`: Old 4-habit system
- `nutrition-plan-routes.ts`, `training-plan-routes.ts`: Old plan system

All routes use `authenticateToken` middleware. Admin routes add `requireAdmin` middleware.

### Frontend Data Flow

**Pattern**: TanStack Query hooks → API routes → Supabase

Each feature has a dedicated hook file in `client/src/hooks/api/`:
- `use-activities.ts`: Activities catalog, registration, history
- `use-training-blocks.ts`: Training blocks and sessions
- `use-daily-vitality.ts`: Weekly/daily PV data
- `use-evaluations.ts`: Health evaluations

**Example Pattern**:
```typescript
// Hook definition
export function useRegisterActivity() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (data) => {
      const { data: { session } } = await supabase.auth.getSession();
      const response = await fetch(`${API_BASE}/api/activities/register`, {
        method: 'POST',
        headers: {
          'Authorization': `Bearer ${session.access_token}`,
          'Content-Type': 'application/json',
        },
        body: JSON.stringify(data),
      });
      return response.json();
    },
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['activity-history'] });
      queryClient.invalidateQueries({ queryKey: ['daily-vitality'] });
    },
  });
}
```

### Authentication Flow

1. Supabase handles auth (JWT tokens)
2. Frontend stores session via `@/lib/supabase` client
3. Backend validates tokens via `authenticateToken` middleware (uses `SUPABASE_JWT_SECRET`)
4. User data is attached to `req.userId` for all authenticated routes

### Database Schema (V2.0)

**Core Tables**:
- `users`: Extended with `activity_level`, `weekly_vitality_goal`, `subscription_status`, `avatar_type`, streaks, total PV
- `activities_catalog`: 65+ activities with METs values (≥3.5 METs)
- `user_activities`: Activity registration history with auto-calculated PV
- `training_blocks`: 36 pre-defined 10-min blocks by type and level
- `user_training_sessions`: Training block completion history
- `daily_vitality`: Daily PV summary (4 main activities + extras)
- `vitality_points_history`: Weekly PV rollup and goal tracking
- `achievements`: 50+ gamification achievements
- `user_achievements`: Unlocked achievements per user
- `evaluations`: Health assessments (IMC, PARQ+, etc.)
- `user_avatars`: Avatar customization and vitality level (1-5)

**Key Functions**:
- `calculate_vitality_points_from_mets(mets, minutes)`: Returns `FLOOR((mets * minutes) / 2)`
- `update_avatar_vitality_level()`: Auto-updates avatar based on weekly PV percentage

### Vitality Points (PV) System

**Formula**: `(METs × minutes) / 2 = Vitality Points`

**4 Main Daily Activities** (2 PV each = 8 PV/day max):
1. Daily Steps Goal (8,000 steps default)
2. Training Block (10-minute block)
3. Active Pause (any METs activity)
4. Meditation/Mindfulness

**Extra Activities**: Any activity from 65+ catalog adds PV based on METs calculation

**Weekly Goal**: Default 28 PV (customizable per user)

**Avatar Evolution** (5 levels based on weekly PV %):
- 0-20%: Level 1 (Apagado)
- 21-50%: Level 2 (Mejora gradual)
- 51-80%: Level 3 (Postura erguida)
- 81-100%: Level 4 (Radiante)
- 100%+: Level 5 (Premium dorado)

## Common Issues and Solutions

### Frontend Build Errors

**Issue**: Vite cannot resolve `@shared/types-v2` or `@/lib/supabase`

**Solution**: These are path alias issues. Check `vite.config.js` and `tsconfig.json` for correct alias mappings:
```javascript
// vite.config.js
resolve: {
  alias: {
    '@': path.resolve(__dirname, './client/src'),
    '@shared': path.resolve(__dirname, './shared'),
  },
}
```

### Mobile Build Issues

**Issue**: App shows blank screen or "localhost refused to connect"

**Cause**: Using `npm run cap:sync` (prod config) but backend is on localhost

**Solution**: Use `npm run cap:sync:dev` which applies `capacitor.config.dev.ts` with `server.url` pointing to `http://10.0.2.2:3000` (Android emulator's host machine)

### Database Migration Errors

**Issue**: Migration fails with "table does not exist"

**Solution**: V2.0 migration creates tables with `IF NOT EXISTS`. If issues persist:
1. Run `npx tsx scripts/check-missing-tables.js` to identify missing tables
2. The migration handles both fresh installs and upgrades from V1

### CORS Errors

The backend CORS config allows:
- `capacitor://localhost` (for mobile app)
- `http://localhost:*` (for dev)
- Production domains from `CORS_ORIGIN` env var

If adding new origins, update `server/config/cors.ts`

## Migration Path from V1 to V2

The V2.0 migration (`scripts/migration-v2.sql`) is **idempotent** and handles both scenarios:

1. **Fresh Install**: Creates all tables from scratch
2. **Upgrade from V1**:
   - Adds new columns to existing `users` table
   - Drops obsolete tables (`subscription_plans`, `nutrition_plans`, `training_plans`)
   - Creates new V2 tables
   - Preserves user data and authentication

**To migrate**: `npm run db:migrate:v2`

## Additional Notes

- **TypeScript**: Both frontend and backend use TypeScript with strict mode
- **Database Access**: Backend uses both Kysely (for complex queries) and Supabase client (for auth and RLS)
- **Code Style**: Components use Radix UI + Tailwind, following a dark theme with `#D3B869` gold accent
- **State Management**: No Redux/Zustand - relies on TanStack Query for server state, React Context for auth
- **Mobile Permissions**: Capacitor automatically adds `INTERNET` permission. Additional permissions require config in `android/app/src/main/AndroidManifest.xml`
